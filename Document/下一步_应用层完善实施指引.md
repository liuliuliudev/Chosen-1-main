# 受控离轨工程：下一步应用层完善实施指引

版本：v0.1  
适用工程：`Coding/` 受控离轨 MATLAB 仿真工程  
目标：在不修改底层动力学和既有传播框架的前提下，把当前“可运行概念仿真版”推进为可审查、可复现、可交付的应用层版本。

---

## 1. 当前版本判断

当前工程已经完成主要的软件实验链：

- 二体引力、J2、大气阻力、低推力和质量变化；
- B0/B1/B2/P 四个基准方案；
- 七个切换高度扫描；
- 密度、帆面积、推力三类敏感性；
- F1-F4 四类故障情景；
- 数值一致性检查；
- 工程资源预算审计；
- 概念监督器及人工观测场景；
- 自动生成结果表、图、动画和证据索引。

现有结果可以用于“本文模型和候选参数范围内”的方案比较，但还不能直接作为硬件可行性、正式赛事合规性或在轨闭环控制的证明。

当前已知状态：

| 项目 | 当前状态 | 说明 |
|---|---|---|
| MATLAB 流程 | 已通过 | `run_tests` 十项测试通过，`run_all` 已有成功日志 |
| 基准方案 | 已完成 | B0/B1/B2/P 可以自动传播和汇总 |
| 参数来源 | 未闭环 | 大气表、推进器、帆面积和供电仍有候选或团队假设 |
| 资源预算 | `unverified` | 账面质量和功率可以计算，但没有器件级证明 |
| 监督器 | 逻辑验证 | 目前只处理人工观测，不改变轨道积分 |
| 设计选择 | 未冻结 | 多个切换点均为非劣点，尚无正式选点规则 |
| 跨机复现 | 未完成 | 尚无第二台电脑的干净会话复现记录 |
| Git 版本 | 未冻结 | 当前仓库没有首个提交，证据索引中的 `gitCommit` 为 `unavailable` |
| 最终材料 | 未完成 | 系统图、状态机图、资格文档、PPT、答辩题库尚未形成交付包 |

---

## 2. 最高优先级结论

下一阶段不应继续盲目增加底层物理模型。首先要补齐以下五件事：

1. 物理输入和赛事要求的来源审计；
2. 时间、推进剂和资源约束下的最终设计选点；
3. 监督器的应用层边界和逻辑证据；
4. 干净环境下的跨机复现与版本固定；
5. 面向评审的正式材料和证据包。

完成这五件事后，工程才可以称为“应用层交付候选版”。

---

## 3. 强制边界

### 3.1 本阶段允许修改

允许修改或新增以下位置：

- `Coding/config/`：来源登记、候选预算、设计规则配置；
- `Coding/scripts/`：输入审计、设计选点、复现检查、报告生成；
- `Coding/src/analysis/`：汇总指标、筛选规则、证据整理；
- `Coding/src/visualization/`：应用层报告图、决策图、审计图；
- `Coding/docs/`：参数、来源、运行、限制和迭代记录；
- `Document/`：对外实施说明、资格文档、PPT 提纲和答辩材料；
- `Coding/data/raw/` 和 `Coding/data/processed/`：经过来源确认后的输入及转换记录。

### 3.2 本阶段禁止修改

未经单独批准，不得修改：

- `Coding/src/dynamics/`；
- `Coding/src/propagation/`；
- 既有 `propagateCase` 的接口和事件语义；
- 既有 B0/B1/B2/P 的物理定义；
- 既有测试的判据，只能在发现真实问题时修正并记录原因；
- 已生成结果表中的数值，不得手工改 CSV 以“修正”结论。

### 3.3 不能混淆的概念

- “程序运行成功”不等于“物理输入已经认证”；
- “预算算术有余量”不等于“硬件可用”；
- “监督器逻辑通过”不等于“已经形成在轨闭环控制”；
- “窗口退出”不等于碰撞概率下降或安全认证；
- “120 km 事件”只表示模型终点，不表示烧蚀、碎裂、落区或地面风险已经完成分析。

# 阶段 A：基线冻结与输入来源审计

## A1. 冻结任务定义

### 目标

把“赛事要求”“团队研究选择”“物理输入”“计算设置”和“仿真输出”分开记录，避免把研究假设写成官方要求。

### 需要完成

1. 找到当前有效的完整赛事规则或官方链接；
2. 记录与本项目相关的原文、版本、页码或网页定位；
3. 明确以下内容的性质：
   - 200-2000 km 是题面范围还是研究对象范围；
   - 120 km 是团队模型终点还是赛事要求；
   - 是否存在正式任务期限；
   - 资格文档页数、摘要字数、匿名和视频格式要求；
4. 保持当前研究定义：550 km 代表轨道、500-600 km 原轨道窗口、120 km 模型终点，除非团队正式批准修改。

### 建议新增文件

- `Coding/config/task_definition.csv`
- `Coding/docs/task_definition.md`
- `Coding/docs/official_rules.md`

### `task_definition.csv` 建议列

```text
itemId,itemName,value,unit,sourceType,sourceLocation,status,notes
```

`sourceType` 至少区分：`official_rule`、`literature`、`team_choice`、`simulation_setting`、`simulation_output`。

### 验收标准

- 每个重要数字都能归类到上述五种来源之一；
- 文档不再把 120 km 或 365 天写成未核实的赛事要求；
- 任何无法核实的项目必须标为 `candidate` 或 `unknown`；
- 规则文件缺失时，工程可以继续运行，但正式结论必须标注“规则待核”。

## A2. 建立参数来源登记

### 目标

为大气、地球常数、卫星、推进器、帆、供电和任务参数建立机器可读的来源登记。

### 建议新增文件

- `Coding/config/input_registry.csv`
- `Coding/scripts/run_input_audit.m`
- `Coding/results/tables/input_audit.csv`
- `Coding/results/tables/input_missing.csv`

### `input_registry.csv` 建议列

```text
parameterId,value,unit,sourceType,sourceTitle,sourceUrl,versionOrDate,
location,applicability,status,conversionNote
```

### 必须登记的输入

- `mu`、`RE`、`J2`、`omegaE`、`g0`；
- 初始质量、干质量、推进剂质量；
- 初始高度、倾角、本体面积、帆面积、阻力系数；
- 推力、比冲、推进器输入功率、占空比；
- 大气表每一个参考节点；
- 计算上限、求解器、误差容差、最大步长；
- 500 km 窗口、350 km 切换点和 120 km 终点。

### 验收标准

- 所有参数均有单位；
- 所有外部来源有标题、链接、版本或访问日期；
- 大气表有原始文件、转换说明和逐行核对结果；
- 输入审计能够区分“已确认”“候选”“未知”；
- `unknown` 项不得被自动填成 0 或基准值；
- 输入审计失败时给出清晰错误，不静默运行正式报告。

## A3. 大气表专项检查

### 需要检查

1. 原始资料是否覆盖 120-650 km 或当前传播所需范围；
2. 高度单位是否从 km 正确转换为 m；
3. 密度单位是否为 kg/m^3；
4. 参考高度是否严格递增；
5. 密度和尺度高度是否为正；
6. 相邻分段在节点附近是否出现明显跳变；
7. 数据适用的太阳活动和地磁条件是什么；
8. 当前 `densityExponential` 的候选表是否与原表逐行一致。

### 注意

如果暂时找不到可靠原表，不得伪造出处。可以保留当前候选表用于软件联调，但所有报告必须显示 `candidate_unverified`。

# 阶段 B：工程预算与最终设计选点

## B1. 完成资源账本闭合

### 目标

把“账面算术预算”推进为“有来源的概念工程预算”。

### 当前账本需要补证的项目

- 平台结构和星载计算机质量；
- 太阳翼、电池和供配电系统质量；
- 推进器和电源处理单元干质量；
- 贮箱和供给系统干质量；
- 帆膜、支撑杆和展开机构质量；
- 姿态执行和监测硬件质量；
- 太阳翼寿命末期功率；
- 食期和电池放电条件；
- 推进模式、展帆模式和组合模式功率；
- 热耗散和连续工作时长；
- 帆展开确认和有效迎风姿态保持。

### 对每一项必须提供

1. 具体器件、任务或论文来源；
2. 质量、功率、工作状态和适用条件；
3. 是否为同一器件工作点；
4. 是否适用于 50 kg 级平台；
5. 是否需要姿态、热或结构条件；
6. `confirmed`、`candidate` 或 `unknown` 状态。

### 验收标准

- 质量项互不重复；
- 推进剂只计入一次；
- 质量总和不超过初始总质量；
- 组合工作模式不沿用单独模式的功率余量；
- 任意关键未知项存在时，总体状态仍为 `unverified`；
- 输入功率、推力和比冲必须能够对应到同一工作点，不能只做数量级比较。

## B2. 冻结切换高度选择规则

### 当前问题

SW325、SW350、SW375、SW400、SW425、SW450 都是非劣点，因此不能只因为 350 km 是基准值就写成“最优”。

### 团队必须先写规则，再看结果

至少选择一种明确规则：

**规则方案一：硬约束筛选**

```text
t_window_exit <= 目标天数
t_120 <= 最大允许天数
propUsed_kg <= 最大推进剂
powerStatus != fail
```

从满足约束的案例中选择推进剂最少或时间最短者。

**规则方案二：分层优先级**

例如：

1. 先保证在最大时间内到达 120 km；
2. 再保证推进剂不超过上限；
3. 再选择窗口退出时间较短的方案。

**规则方案三：加权评分**

只有在团队能够解释权重来源时使用。权重不能为了让 350 km 获胜而事后调整。

### 建议新增输出

- `results/tables/design_decision.csv`
- `results/tables/design_constraints.csv`
- `results/figures/design_decision.png`
- `Coding/docs/design_freeze.md`

### 输出至少包括

- 候选点；
- 是否满足每一条约束；
- 窗口退出时间；
- 120 km 时间；
- 推进剂；
- 推力开机时间；
- 故障退化；
- 资源状态；
- 最终推荐点；
- 未选择其他点的原因。

## B3. 保留不确定性边界

在没有可靠概率分布前，不要直接宣称成功率。优先生成确定性边界：

- 密度倍率 0.5、1.0、2.0；
- 帆面积 5、10、15、20 m^2；
- 推力 10、20、30、40 mN；
- F1-F4 故障；
- 最终选点在最差情景下的结果。

如果后续有时间，再增加 100-200 组固定随机种子的蒙特卡洛，并保存样本配置、随机种子、失败样本和分位数。

# 阶段 C：监督器应用层验证

## C1. 先冻结监督器的定位

当前工程的监督器应明确称为：

> 基于预置观测的离轨任务监督逻辑演示。

不能称为：

- 已实现的在轨智能控制；
- 已验证的传感器闭环；
- 已完成的能源调度；
- 已完成的姿态控制；
- 已完成的故障诊断系统。

## C2. 在当前边界内的实现方式

由于本阶段禁止修改 `propagateCase`，监督器只做应用层回放：

1. 从案例结果中读取时间、阶段、燃料和帆状态；
2. 构造对应的模拟观测；
3. 调用 `deorbitSupervisor`；
4. 保存命令、下一状态、理由码和输入观测；
5. 检查输出是否符合预先写定的规则；
6. 生成故障响应表和状态转换图。

### 建议新增文件

- `Coding/scripts/run_supervisor_replay.m`
- `Coding/src/analysis/summarizeSupervisorReplay.m`
- `Coding/results/tables/supervisor_replay.csv`
- `Coding/results/figures/supervisor_state_machine.png`

### 必须覆盖的情景

- 退役许可拒绝；
- 基础功率不足；
- 推进功率不足；
- 姿态不可用；
- 推进器失效；
- 燃料耗尽；
- 切换条件达到；
- 展帆未确认；
- 半展帆；
- 帆完全失效；
- 功率观测未知；
- 到达模型终点。

### 验收标准

- 每个情景都有唯一理由码；
- 未知观测默认进入安全动作；
- 展帆命令只允许发出一次；
- 任何状态转换都有输入条件和输出命令；
- 监督器结果不改变已有 B0/B1/B2/P 轨迹；
- 报告明确说明这是逻辑回放，不是连续动力学闭环。

## C3. 如果未来必须实现真实闭环

真实闭环需要增加“积分片段边界接收命令”的框架接口，涉及传播器。该工作不属于本指引范围，必须另立任务并重新评审：

- 命令更新时刻；
- 观测采样周期；
- 传感器延迟和噪声；
- 命令保持和故障锁存；
- ODE 分段重启；
- 监督器状态与轨迹状态的映射。

在没有单独批准前，不要通过修改现有传播器来“偷偷接入”监督器。

## E3. PPT 和答辩题库

PPT 至少回答：

- 为什么需要受控离轨；
- 为什么选择 550 km 代表案例；
- 为什么采用先推后帆；
- 350 km 或最终选点如何得出；
- P 与 B1/B2 的时间和燃料取舍；
- 大气不确定性如何影响结论；
- 推进器参数是否来自同一工作点；
- 帆是否真的能保持有效迎风面积；
- 监督器当前已经实现到什么程度；
- 为什么终止于 120 km；
- 哪些功能明确没有实现；
- 失败案例改变了什么判断。

至少准备十个高概率问题，每个问题都必须能指向一个数据表、图或参数来源。

# 5. 推荐分工

如果仍由五人团队执行，可以按以下方式分工：

| 角色 | 主要任务 | 必须交付 |
|---|---|---|
| 系统负责人 | 任务定义、规则核查、阶段冻结 | `task_definition.md`、风险清单、最终选点批准 |
| 参数与来源负责人 | 大气、推进器、帆、供电资料 | `input_registry.csv`、来源审计表 |
| 资源与设计负责人 | 质量、功率、选点规则 | 预算更新、`design_decision.csv` |
| 控制与验证负责人 | 监督器回放、故障情景、测试 | `supervisor_replay.csv`、测试报告 |
| 数据与材料负责人 | 图表、证据索引、文档、PPT | 交付包、复现日志、答辩题库 |

每个人必须能够独立解释至少一个模型公式、一个结果表和一个失败案例。

# 7. 建议的最小完成路线

如果时间有限，按以下顺序完成：

1. 建立 Git 首个提交；
2. 完成任务定义和输入来源登记；
3. 完成大气表和关键硬件参数的候选/确认标记；
4. 冻结切换点选择规则并生成设计决策表；
5. 完成监督器回放和状态机图；
6. 保存快速演示的表、MAT、日志和参数快照；
7. 完成另一台电脑复现；
8. 完成系统图、资格文档、PPT 和答辩题库；
9. 再考虑蒙特卡洛、额外求解器或更高级物理模型。

在第 1-8 步完成前，不应把时间投入到 Simulink、ZYNQ、自动优化、复杂再入、机器学习或精致三维动画。

# 8. 完成判定

满足以下条件后，可以把版本标记为“应用层完善候选版”：

1. 输入来源审计有结果，未知项明确列出；
2. 最终设计点有预先写定的选择规则；
3. 监督器逻辑有完整情景回放，但没有夸大为闭环；
4. 工程预算和故障边界在报告中可追溯；
5. `run_quick_demo`、`run_tests`、`run_all` 可重建结果；
6. 第二台电脑完成干净会话复现；
7. Git 提交、参数快照、日志和输出索引齐全；
8. 系统图、状态机图、资格文档、PPT 和答辩题库完成；
9. 报告中的所有结论都限定在“本文模型和参数范围内”；
10. 没有把候选输入、逻辑情景或模型终点写成已经验证的飞行能力。

完成以上条件后，才进入可选增强阶段。
